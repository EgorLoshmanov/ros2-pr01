# PR01 — граф ROS 2, разрыв связи и восстановление

## Окружение

- Ubuntu 26.04.1 LTS
- Architecture: aarch64
- ROS 2: Lyrical
- RMW: rmw_fastrtps_cpp
- Рабочий ROS_DOMAIN_ID: 16
- Неисправный ROS_DOMAIN_ID: 17
- Gazebo Sim: 10.5.0
- Запуск: Docker + noVNC

## Исправный граф

В домене 16 обнаружены две ноды:

- `/turtlesim`
- `/teleop_turtle`

Основная связь:

```text
/teleop_turtle
      |
      | publish: /turtle1/cmd_vel
      | type: geometry_msgs/msg/Twist
      v
/turtlesim
      |
      | publish: /turtle1/pose
      | type: turtlesim_msgs/msg/Pose
      v
позиция черепахи
```

Нода `/teleop_turtle` публикует команды движения в топик
`/turtle1/cmd_vel`.

Нода `/turtlesim` подписана на `/turtle1/cmd_vel` и публикует
текущую позицию черепахи в `/turtle1/pose`.

Тип `/turtle1/pose`:

```text
turtlesim_msgs/msg/Pose
```

Поза до управляющей команды:

```text
x: 5.517826557159424
y: 7.560268878936768
theta: 1.5839999914169312
```

После нажатия клавиши в рабочем домене:

```text
x: 5.491209030151367
y: 9.576092720031738
theta: 1.5839999914169312
```

Координаты изменились, следовательно управление работает.

Частота публикации `/turtle1/pose` составляет приблизительно:

```text
62.49 Hz
```

Измерение выполнялось примерно 15 секунд.

## Разрыв связи

Нода `/turtlesim` была оставлена в домене:

```text
ROS_DOMAIN_ID=16
```

Нода `/teleop_turtle` была остановлена и заново запущена в:

```text
ROS_DOMAIN_ID=17
```

После этого в домене 17 обнаруживалась только нода:

```text
/teleop_turtle
```

Нода `/turtlesim` в домене 17 не обнаруживалась.

Попытка получить сообщение из `/turtle1/pose` в домене 17
завершилась по таймауту:

```text
exit=124
```

Это подтверждает отсутствие обмена сообщениями между нодами,
находящимися в разных ROS_DOMAIN_ID.

Дополнительно было проверено управление.

Поза перед нажатием клавиши из домена 17:

```text
x: 5.464591026306152
y: 11.088889122009277
theta: 1.5839999914169312
```

Поза после нажатия клавиши из домена 17:

```text
x: 5.464591026306152
y: 11.088889122009277
theta: 1.5839999914169312
```

Координаты не изменились, поэтому команда управления из domain 17
не дошла до `/turtlesim`, работающего в domain 16.

## Причина неисправности

`ROS_DOMAIN_ID` разделяет участников ROS 2 на независимые DDS-домены.

Ноды, работающие с разными значениями `ROS_DOMAIN_ID`, в данном
эксперименте не обнаруживают друг друга и не обмениваются сообщениями.

Изменение переменной окружения:

```bash
export ROS_DOMAIN_ID=17
```

не изменяет домен уже запущенного процесса.

Для изменения домена ноду необходимо остановить и запустить заново
с новым значением `ROS_DOMAIN_ID`.

## Восстановление

Нода `/teleop_turtle` была остановлена и снова запущена с:

```text
ROS_DOMAIN_ID=16
```

После этого снова были обнаружены обе ноды:

```text
/teleop_turtle
/turtlesim
```

Получение сообщения из `/turtle1/pose` снова стало успешным:

```text
exit=0
```

Поза перед контрольным нажатием клавиши:

```text
x: 5.491209030151367
y: 9.576092720031738
theta: 1.5839999914169312
```

Поза после контрольного нажатия:

```text
x: 5.464591026306152
y: 11.088889122009277
theta: 1.5839999914169312
```

Координаты изменились.

Следовательно, после возврата `/teleop_turtle` в domain 16
связь между нодами и управление черепахой были восстановлены.

## Вывод

В ходе работы был исследован граф ROS 2, изучены ноды, топики,
publisher/subscriber-связи и типы сообщений.

Эксперимент показал, что разные значения `ROS_DOMAIN_ID`
изолируют ROS 2-ноды друг от друга.

После возврата нод в один домен связь и управление успешно
восстанавливаются.
